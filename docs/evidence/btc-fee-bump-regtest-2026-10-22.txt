Bitcoin and Litecoin fee bump (own-output CPFP): regtest verification, 2026-10-22
================================================================================

What this is
------------
Branch btc-fee-bump adds an opt-in fee bump to ferryd (--bump on; off by default). The party that
needs a spend confirmed (Z for tx_redeem and tx_punish, B for tx_refund) spends its own output of
that spend in a version-2 child that pays a higher fee, and replaces that child with a better one
as the deadline nears. No presigned transaction, signature, message or PROTOCOL_VERSION changes
(a golden test pins every presigned txid and sighash). tx_cancel is not bumped, on purpose.
Bitcoin and Litecoin REMAIN OFF mainnet until the bump has been reviewed (docs/THREAT-MODEL.md):
ferryd refuses to start with --bump on (or FERRY_BUMP=on) on a Bitcoin or Litecoin mainnet.

Everything below ran on regtest, on one Mac, in Docker containers named ferry-bump-* on host
ports 28443-28447 (and ferryd test processes on 28100-28199). Nothing touched a public network.
The commands are the lines that start with "$". The raw output follows this summary; sections
are numbered as in the script that produced it. Nodes: bitcoin/bitcoin:28.1 (the image Ferry
pins) and uphold/litecoin-core:0.21@sha256:46ebcaa6... (Litecoin Core 0.21.5.6).

What did NOT run, or is not proven (UNVERIFIED)
-----------------------------------------------
 - Anything on a public network: relay and mining of packages by other nodes and miners, 1P1C
   package relay across peers, miner behaviour. One node only.
 - Bitcoin Core 29 and 30 (the plan asks to rerun on them: their floors are 0.1 sat/vB and
   cluster mempool changed policy). Only 28.1 was available and pinned.
 - A Litecoin swap through ferryd (--chain ltc): only the Litecoin building blocks ran.
 - estimatesmartfee with real data: a regtest node has none, so the daemon's estimate branch is
   covered by unit tests only (the floors branch is what the regtest swaps exercised).
 - A reorg of the parent with ferryd running (the reorg check is at the RPC level).
 - Several swaps bumping at once from one wallet; an encrypted (locked) wallet.
 - Z's package replacing a cancel that is already in the mempool (package RBF against the
   cancel). Not needed by the design (a redeem the node never took cannot be first-sent after
   T1 - delta, bump or not), and ferry-core's state machine has moved on by then (see below).
 - The daemon hook's handling of a node that refuses a send ("insufficient fee", or litecoind
   without replacement answering txn-mempool-conflict): written once and retried, covered by
   reading and by the child-builder tests, not by a swap.
 - Third-party payout_to forwarding (design section 5.4): not built.
 - The plan's INFERRED "cluster of three blocks package RBF" extra defence: not built, not tested.

Found in review, written down and not fixed
-------------------------------------------
 - The daemon takes any spender of the parent's payout output, as the node's mempool reports it,
   for its own child (spent_by.first()). If something else spent the unconfirmed payout, a bump
   would try to replace it. The wallet does not choose such an output on its own (an output of an
   unconfirmed transaction that did not come from the wallet is not trusted), so this needs a
   manual spend.
 - The bump stops when the other side's competing spend is seen, even unconfirmed, because
   ferry-core moves the swap on at once (Z: Redeeming -> Cancelled when a call-off is in the
   mempool; B: Refunding -> Punished when a penalty is). A redeem or refund put back as a package
   could still have replaced it. ferry-core was not changed.
 - Before this change, and not caused by it: on Litecoin (no packages) a spend that the node
   evicted is re-sent only while its timing rule allows a first broadcast (rebroadcast.rs); the
   bump cannot help there, because it needs the spend in the mempool, or a package.

Findings that differ from the design plan
-----------------------------------------
 - testmempoolaccept on a package cannot vouch for a child-pays-for-parent package on Core 28.1:
   each transaction is judged on its own fee, so it refuses the parent the child is there to lift
   (section 3 prints it). Only submitpackage applies the package feerate. The daemon therefore
   dry-runs a child that goes out alone and not a package.
 - The parent must still meet the static minrelaytxfee by itself (section 2). The planner reports
   it as "cannot be bumped" instead of trying.
 - Litecoin Core 0.21.5.6 has replacement OFF by default (sections 13 and 14): on a default
   litecoind a bump can be sent once but not replaced.
 - Plan 5.2 steps 2 and 3 contradict each other as written (a target that includes "current
   package feerate + one increment" is never reached); built as: hold if the package already pays
   the wanted rate, else bid max(wanted, current + increment).
 - A child is judged alone when its parent is already in the mempool, so it must clear the
   mempool floor on its own as well; added.
 - lockunspent cannot lock an output that a mempool transaction already spends, so the
   locked-coin refusal is tested before the first child.
 - -blockmintxfee needs -mintxfee as well, or the wallet's own transactions are left out too.
 - submitpackage with a parent that is already mined answers "transaction failed" yet accepts
   the child (section 4), so a lost race is harmless, but the daemon checks first.

What failed while the tests were being built (all fixed, or recorded above)
--------------------------------------------------------------------------
 - bitcoind 28.1 refused to start with -maxmempool=1 ("-maxmempool must be at least 5 MB"), even
   on regtest; the tests use 5 and fill it with about 30 transactions of 65 kvB.
 - The first version of the package test asserted that testmempoolaccept accepts the package:
   it does not (see Findings); the test now records the answer instead and relies on
   submitpackage, and the daemon does not dry-run packages.
 - The first run of the primitives test against litecoind: a valid replacement was refused with
   txn-mempool-conflict (-mempoolreplacement is 0 by default); the test now accepts both
   settings and says which one it met.
 - lockunspent refused an output that a mempool transaction already spends, so the locked-coin
   check had to move before the first child.
 - A filler-transaction helper passed its input in fundrawtransaction's options, where it is
   ignored ("preselected coins ... do not cover"); the input belongs in the raw transaction.
   Fixed. (Amounts and maxfeerate are sent as text, not as JSON floats such as 1e-5, as a
   precaution; that was not shown to matter.)
 - A scripting slip: cargo fmt was run over whole crates once and reformatted unrelated files in
   ferryd; those hunks were reverted before commit, and only the new files are formatted since.
 - In a full run of this matrix on commit 940c5f0 the refund swap test (section 7) failed once:
   Z ended "Refunded" instead of "ZecReclaimed" (left: ("Refunded", "Refunded"), right:
   ("ZecReclaimed", "Refunded")); every other section passed. Eight reruns of that test did not
   reproduce it. The likely cause is a test race: the state reads ZecLocked as soon as Z's ZEC
   lock is queued, and a Z stalled before the lock is sent has nothing to reclaim. Z was not
   running the bump (it was B that did), so the bump is not implicated. That run's raw output is
   not in this file (the log was replaced by the run below). The test now waits for the lock's
   timeline entry before stalling Z, and passed ten reruns in a row and then this whole matrix.
 - An independent review of the code (c1ab771) found: no hard mainnet gate (added), a punish that
   a wide urgent window could make urgent (fixed, the window is bounded), a package attempted
   against a parent mined meanwhile and a parent that went in without being marked sent (fixed),
   refusal notes that varied with every txid (fixed), a rate ceiling that an unconfirmed
   ancestor could trip every block (fixed), and test and wording nits (fixed).

How to reproduce
----------------
The nodes are the "docker run" lines; each test says in its doc comment which node it needs
(crates/ferry-btc/tests/regtest_rpc.rs, crates/ferryd/tests/two_daemons.rs). A fresh node is
started for each test that raises the mempool floor, because the floor outlives a test.
